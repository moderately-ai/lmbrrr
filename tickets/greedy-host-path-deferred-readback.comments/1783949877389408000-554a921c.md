DESIGN UPGRADE (2026-07-13, user question: why not fully decouple token readback from compute?): the answer is IT IS POSSIBLE and the current every-8 flush is the cheap 80% version, not a fundamental limit. Current anatomy: the device chain already decouples the FEEDBACK loop (next forward's input is the on-device argmax id — no readback needed to keep generating); the host reads ids only for EOS detection + streaming. But the flush does it BLOCKINGLY: host stops encoding, waits for the whole queue (fine, GPU still busy), then the GPU runs dry while the host scans EOS and re-ramps encoding (~1ms to first re-commit at CPB=100) -> ~0.1-0.3 ms/token bubble at N=8.\n\nFULL DECOUPLING (phase 2, do after the flag sweep): (a) device side — after each argmax, a tiny kernel appends the id into a SHARED-storage-mode ring buffer and bumps a monotonically-increasing ready-counter (unified memory: host reads it coherently with zero copy, no PCIe analogue on Apple silicon); (b) host side — encoder thread encodes ahead unconditionally (bounded ahead-window K to cap EOS overshoot waste); a reader thread polls the counter (or uses per-command-buffer completion handlers, coarser), consumes ids as they land, streams per-token (KILLS the 8-token streaming burst — jitter p95 drops from ~24ms to ~3ms), checks EOS, and flags the encoder to stop. GPU never starves; host never blocks the GPU.\n\nWHY IT IS NOT ALREADY DONE (honest order-of-work): (1) candle's tensor API has no non-blocking readback — to_vec1 is waitUntilCompleted; the ring+counter needs fork surgery below the tensor abstraction (we own the fork, so this is days not weeks); (2) the prize was estimated at 0.1-0.3 ms/token (~3-8%) and the census ticket (eval-host-loop-budget-census) exists to MEASURE it before building; (3) EOS overshoot economics are the same as today's, just tunable via K. EXECUTION ORDER: census -> if readback-wait >= 0.15 ms/token, run the cheap READBACK_EVERY sweep for the quick win AND build the ring-buffer decoupling as the real fix (it also wins on jitter, which the flag sweep makes WORSE); if census says < 0.15 ms/token, the flag sweep dies but the ring buffer may still be justified on jitter alone once eval-harness-validity-fixes' p95/p99 columns are standing.
