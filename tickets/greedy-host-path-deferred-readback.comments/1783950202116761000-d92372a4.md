CANDLE-CHANGES ASSESSMENT (2026-07-13, spec-reviewed; UPSTREAM CANDIDATE). The idiomatic mechanism per the Metal spec + API docs, and exactly what candle needs to grow:

MECHANISM (why this shape): MSL section 4.8 (Metal 3.2+) defines coherent(device) — but its coherence scope is GPU THREADS only; the CPU observing GPU writes MID-command-buffer is not in its contract. The officially sanctioned CPU-visibility primitive is MTLSharedEvent: GPU encodes encodeSignalEvent(event, value) at an encoder boundary; the signal makes all prior writes visible and MTLSharedEventListener fires an async host callback at that value. MTLSharedEvent is macOS 10.14+ — NO OS gate, works on every fleet machine (unlike the packed_numeric lane). CPU polling of a coherent/shared buffer mid-execution does work on Apple silicon unified memory but is contract-grey — fine as a measured experiment, wrong for upstream.

FACTS VERIFIED IN THE TREE: (a) candle Metal buffers already default to StorageModeShared + HazardTrackingModeUntracked (candle-core/src/metal_backend/device.rs:123) -> the host can read a result ring ZERO-COPY once visibility is signaled; (b) the fork binds Metal via objc2-metal 0.3.2 with block2 enabled -> MTLSharedEvent/MTLSharedEventListener bindings + closure callbacks are available without new deps; (c) our Commands layer already owns encoder lifecycle (CPB batching) -> a signal is just an encoder split + one encoded command.

CANDLE CHANGES (three layers, ~400 LOC total, days not weeks):
1. candle-metal-kernels (metal wrapper): SharedEvent newtype (device.newSharedEvent()); Commands::signal_event(&event, value: u64) — end current compute encoder, encodeSignalEvent on the command buffer, reopen encoder lazily on next dispatch; SharedEventListener wrapper taking a Rust closure (block2) with notify(event, value, cb).
2. candle-core metal backend: MetalDevice::signal_progress(&event, value) plumbing to Commands; unsafe MetalStorage::host_view_unsynchronized() -> &[u8] returning the shared buffer contents WITHOUT synchronize — documented contract: only regions covered by a received event signal are valid.
3. lmbrrr (consumer, generate.rs device chain): allocate a [max_new_tokens] U32 id ring once; write token i's argmax id into ring[i] (slice-set dispatch, or argmax-with-dst-offset for zero extra dispatches); signal value i+1 per token (encoder split per token ~ noise vs 340 dispatches/token); listener thread consumes ring[..value] — detokenize, stream PER-TOKEN (jitter p95 drops ~24ms -> ~3ms), EOS-check, sets AtomicUsize stop flag; encoder loop checks the flag and bounds run-ahead to K tokens (EOS overshoot cap, replaces today's fixed 8).
Hazard interaction: buffers are untracked + our fences are manual; the ring is GPU-write/host-read only (no GPU reader), so NO fence changes needed.

UPSTREAM SHAPE: candle PR 'metal: shared-event progress signaling + unsynchronized host views' — layers 1+2 only, generic for any streaming-decode consumer (candle's own generation examples want this too). lmbrrr keeps layer 3. Sequencing: census still gates the throughput claim, but the jitter win is independent — if census says the throughput prize is small, this can still ship as the streaming-latency fix with the p95/p99 columns (now standing, bd2fbb0) as its gate.
