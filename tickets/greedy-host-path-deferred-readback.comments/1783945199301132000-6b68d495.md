EXECUTOR PROCEDURE (self-contained).

WHY: in greedy device-chain decode (src/generate.rs), the host reads the committed token id back every step to (a) detect EOS and (b) detokenize incrementally. The readback forces a command-buffer flush + wait per token; the GPU then sits idle while the host does tokenizer work. Deferring readback lets the GPU run ahead N tokens.

DESIGN: keep the device-side chain exactly as is (argmax id tensor per step, remap_head_id applied). Instead of `.to_vec1()` per step, accumulate the per-step id tensors in a ring (they are 1-element U32 tensors already on device; cat every N into one [N] tensor and read back once). Read back every READBACK_EVERY steps (start N=8). On readback, scan the N ids host-side for EOS; if EOS found at position k, truncate to k and stop (the extra <N-k speculatively-computed steps are discarded — this is pure waste heat, not a correctness issue, because greedy decode has no state that the host influences mid-chain). TRAP: max-new-tokens boundaries — flush the partial window at the end. TRAP: the incremental detokenizer/stream printer now receives tokens in bursts of N; batch its input (the bench path doesn't print, so this only affects `run`).

WHERE: src/generate.rs device-chain branch (the loop that calls model.remap_head_id + pending token bookkeeping). Flag: `--readback-every N` on run/bench (default 1 = current behaviour, so the change is inert until flagged; flip default only after the eval ships).

GATES: `cargo nextest run` (59) then rebuild `cargo build --release`. Text gate: `./target/release/lmbrrr run --quantized-manifest artifacts/minicpm-v46-q4k-full-text/manifest.json --quantize-lm-head q4k --prompt "Explain how tides work." --max-new-tokens 256 --readback-every 8` must produce BYTE-IDENTICAL text vs --readback-every 1 (this change reorders host work only; token ids must not change). Also test an EOS-terminating prompt (short answer prompt, e.g. "What is 2+2? Answer with one word.") to exercise the truncation path, and confirm token count matches the N=1 run exactly.

MEASUREMENT (per eval-protocol-ambient-control): bench A/B via the flag on one binary, palindrome N=1, 8, 32, 32, 8, 1: `./target/release/lmbrrr bench --quantized-manifest artifacts/minicpm-v46-q4k-full-text/manifest.json --quantize-lm-head q4k --warmup 1 --iterations 3 --profile medium --readback-every N` (+ --profile long). Metric: median steady_state_tokens_per_second. Sweep is cheap — also try 4 and 16 if 8 vs 32 differ.

EXPECTED: bench-loop greedy is host/sampling-bound at the margin (32k-head experiment showed device-side savings under-realize in bench tok/s); prize is the per-step flush+wait, previously estimated 0.1-0.3 ms/token. DECISION: >= +2% non-overlapping on either profile -> flip the default to the winning N, update ticket + campaign log, refit cost model (greedy_step_ms changes -> `python3 evals/run_spec_suite.py --arm round4=artifacts/dspark-drafter-round4 --split calibration --per-class 3 --reps 1 --gamma 6 --tag refit-readback`). NOTE: this changes the GREEDY baseline that speculation is judged against — after shipping, re-run one spec validation pass to keep speedup ratios honest. Below +2%: record numbers, keep flag, close as measured-flat.

SPEC-LANE VARIANT (optional follow-up, separate measurement): the dspark verify loop reads back the packed accept/commit buffer every round and genuinely needs it (host schedules the next round) — NOT deferrable there; do not attempt. Scope is greedy only.
