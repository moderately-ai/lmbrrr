DESIGN REVISION after fence-machinery validation (2026-07-13, read candle-metal-kernels/src/metal/commands.rs in full): per-token encoder splits are the WRONG shape in our fork. Every encoder start waits on ALL live prev-writer fences (commands.rs command_encoder(): wait_for_fence loop over prev_ce_outputs — required by HazardTrackingModeUntracked), and the CPB sweep already priced encoder boundaries at roughly 40us each (100-vs-50 = +3-4% over ~3.4 fewer boundaries/token; see the constant's comment). A per-token split would burn ~1% of the step — up to half the readback prize.\n\nREVISED SHAPE — piggyback on existing boundaries: encode signalEvent(value = total dispatches encoded so far) as the LAST command in commit_swap_locked, right before commit(). Zero marginal encoder boundaries; at CPB=100 that is ~3.4 signals/token — SUB-token granularity. Host side: the encode loop records dispatch_index at each token's argmax (known at encode time); the SharedEventListener on value V marks readable every token whose argmax dispatch_index <= V, reads its id from the shared ring (visibility guaranteed by the signal), streams/EOS-checks. No CPB change, no fence changes (host is not a GPU encoder; the ring is GPU-write/host-read only). Precedent already in-tree: commands.rs end_encoding() already uses addCompletedHandler for fence-map cleanup — the callback pattern is exercised.\n\nCANDLE DELTA (upstream PR, revised): (1) Commands::attach_progress_event(event) + the signal encode inside commit_swap_locked + a dispatch-counter accessor (the compute_count atomic already exists — expose a monotonic total rather than the per-CB reset counter); (2) unchanged: SharedEvent/Listener wrappers + unsafe host view. Smaller and less invasive than the encoder-split version — better upstream odds too.
