EXECUTOR PROCEDURE — adaptive-sync evaluation (the remaining open question on this ticket; the on-device assembly + --lag-schedule prototype is BUILT and measured: drain kill is real at -0.4..-0.5 ms per drafted round, but one-round-stale width decisions tax strong classes, so the flag defaults OFF).

HYPOTHESIS: lag only when the width decision is INSENSITIVE to staleness. The scheduler picks width w from drafter confidences; when the confidence vector sits far from every width-decision boundary, the stale decision equals the fresh one and lagging is free; near a boundary it isn't.

PHASE 1 — OFFLINE SIM (no code on the hot path; do this first, it can kill the idea for free):
1. Data: every dspark-run/suite report already carries per-round `proposal_confidences` (added this campaign) plus chosen widths and accept outcomes. Generate a fresh corpus if needed: `python3 evals/run_spec_suite.py --arm round4=artifacts/dspark-drafter-round4 --split validation --per-class 3 --reps 1 --gamma 6 --tag lag-sim-corpus` (any quiet run works; the sim only needs the logs, not clean timing).
2. Write evals/sim_adaptive_lag.py: replay each round; compute the width the Appendix-A scheduler would choose from round t confidences (fresh) vs round t-1 (stale). Trigger candidates: (a) margin trigger — distance of the confidence statistic from the nearest width boundary, sweep thresholds; (b) width-agreement oracle (upper bound) — lag exactly when stale width == fresh width.
3. Score with the measured constants: lagged round saves 0.45 ms (midpoint of the measured drain kill); a width mismatch costs the cost-model delta between running stale-w vs fresh-w given the round's realized accept length (use T_round = fixed + draft + verify[w+1] from artifacts/spec-round-cost-model-fusion.json to price both, plus lost/extra committed tokens via the accept outcome).
4. DECISION GATE: report per-class EV (ms/round saved net of regret) + fraction of rounds lagged. Proceed to Phase 2 only if the ORACLE variant shows >= +0.15 ms/round net on every class (if even perfect boundary knowledge can't clear that, the mechanism is dead — record + close) AND some practical margin threshold captures >= 60% of the oracle EV.
PHASE 2 — RUNTIME TRIGGER: implement the winning margin trigger inside the --lag-schedule path in src/commands/dspark.rs (the device_proposal branch): compute boundary distance from prev_draft_confidences before choosing to lag; sync (materialize proposal, current default behaviour) when within threshold. Gates: nextest 59 -> rebuild; stub oracle; tree-check; committed-text similarity vs flag-off (NOT byte-identical — width choices legitimately change rounds, text must still be equal because verification is exact; if text differs the verifier has a bug, stop). Measurement: validation suite A/B flag-on vs flag-off, --per-class 3 --reps 3, per-class means; DECISION: no class regresses > 1% and overall mean >= +1.5% -> default on; else keep flag + record.

RECEIPTS: --lag-schedule always-on measured (this ticket's comments): weak classes +2-4%, strong classes -2-5% (width staleness). The drain saving is real; the trigger is the whole game.
