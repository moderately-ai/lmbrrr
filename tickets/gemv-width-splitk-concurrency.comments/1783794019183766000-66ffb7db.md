mc kernel diagnosis complete (2026-07-11, read in full: quantized.metal 7896-8135). The mc variants DO share weight reads (block hoisted to registers once per (ib,row)), but the NC column loop is SERIAL per thread — full unpack+FMA chain per column, so arithmetic scales linearly in m while the kernel is arithmetic/latency-bound at k=1024 (not bandwidth-bound). Measured signature matches exactly: lm_head q4k/bf16 n=2 = 1.91x n=1. Fix design (option B): one simdgroup per column within the threadgroup (TG = NC x 32), quantized block staged once through threadgroup memory (or re-read from L1 - it is resident), columns computed in parallel -> time ~flat in m up to NC, weight traffic unchanged. Alternative (option A): distribute (position, column) pairs across lanes - more invasive against the q4k ix/it unpack structure.

SECOND finding, larger for decode: the BASE mv kernel achieves only ~90 GB/s on the lm_head shape (248k rows x k=1024). nb = ne00/QK_K = 4 blocks/row means each thread does ONE block iteration per row-pass - work granularity too fine, launch/index arithmetic dominates. Roofline at 350 GB/s = 0.41 ms vs measured 1.58 ms: ~3x on the single largest op of EVERY forward (l=1 decode included). A k-split or multi-row-per-thread restructure for small-k/huge-n shapes is likely the single biggest remaining kernel win now that the deltanet numbers are corrected. Sequence: base-mv small-k efficiency first (helps every token), then mc column-parallelism (helps verify chunks), then SDPA vector->full for l<=12.
