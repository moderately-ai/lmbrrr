STREAMING KERNEL REFUTED + THE REAL BOTTLENECK IS OCCUPANCY (2026-07-17, WHITE-BOX GPU COUNTERS via gpudebug on isolated `gguf bench-deltanet` captures; this OVERTURNS the wall-clock/CAP-sweep inference that prefill is S-traffic-bound).

Built the single-dispatch streaming prefill kernel (gated_delta_prefill, candle 6c6531d4) two ways: (a) S carried in a 128-float register column -> 4.11s (register spill); (b) S device-resident in-place -> 3.86-3.97s. BOTH byte-correct, BOTH SLOWER than the host-looped chunk (3.76s). Isolated bench (Bonsai shapes, no MLP/attn): chunk 12.54 ms/seq, stream 14.75 (+18%).

**gpudebug counters (--gpu-state high, --embed; stream vs chunk):**
- kernel_occupancy: **7.93% vs 8.01%** (SAME — occupancy is NOT the differentiator)
- occupancy_manager_target: 99.97% / 99.95% (the GPU WANTS full occupancy)
- gpu_bandwidth: **2.06% vs 13.34%** of peak (NEITHER is memory-bound -> S-traffic hypothesis REFUTED)
- alu_util: ~6%; instruction_throughput_limiter 26% / 16%; active at low util across the board
- l1_eviction_rate: **0.55 vs 0.01** (the ONLY big stream/chunk difference)

**Mechanism 1 (why the kernels are slow at all): LATENCY-BOUND at ~8% occupancy.** xctrace says both are 100% GPU-busy at Max clocks (busy_frac 1.0, gaps ~1ms/13s), yet every counter is low and the manager wants 100% -> the GPU is busy STALLING. The per-position recurrence is barrier-chained (serial across positions); 8% occupancy can't hide that latency. Occupancy is capped by threadgroup memory (4x [TILE*128] f32 stages ~= 24-26KB -> ~1 threadgroup/core) + register pressure (manager_target 100%, achieved 8%, low l1_evict = register/tg-mem capped, NOT a manager decision). This is the SAME kernel (gated_delta_chunk_bf16) the VERIFY path runs every spec round (~27% of the verify step), so occupancy is a whole-pipeline lever, not just prefill.

**Mechanism 2 (why streaming loses to chunk): L1 thrash from in-place S.** Chunk reads read-only `state_in` + writes separate write-only `state_out` (clean lines evict free) -> eviction 0.01. Streaming reads+writes the SAME `s_dev` in place across 20 tiles in one long dispatch -> dirty S lines writeback+reread as each tile's working set evicts them -> eviction 0.55 -> +18%. Fixable with a read/write ping-pong, but that only MATCHES chunk (both latency-bound), can't beat it. So single-dispatch streaming has no path to win here (its only theoretical edge, fewer dispatches, is moot: both are 100% busy and the recurrence is serial).
