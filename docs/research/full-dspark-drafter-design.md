# Full DSpark Drafter Design

Date: 2026-07-10

Ticket: `design-full-dspark-drafter`

Source paper: `docs/research/papers/dspark-2607.05147v1.pdf` (DSpark: Confidence-Scheduled Speculative Decoding with Semi-Autoregressive Generation, DeepSeek-AI + PKU, July 2026).

This note translates the full DSpark method into an implementation plan for the MiniCPM-V-4.6 text decoder (Qwen3.5 hybrid: 18 Gated DeltaNet linear-attention layers + 6 full-attention layers, hidden size 1024, intermediate 3584, vocab 248,094 with tied embeddings) running on Candle/Metal. Correction 2026-07-10: an earlier draft of this note said hidden 3072 — that was the trace feature dimension (3 capture layers × 1024 concatenated), not the model width; all dimensions below use the true h = 1024 from the vendored config. The target is the complete method — parallel backbone, semi-autoregressive Markov head, confidence head with STS calibration, and hardware-aware verification scheduling — not confidence scheduling bolted onto an EAGLE-style drafter. The recurrent EAGLE runner and any DFlash-only path are comparison baselines, never investment targets; the DFlash baseline is obtained from the DSpark runner with the Markov head disabled.

## 1. Runtime components

### 1.1 Parallel backbone (DFlash-derived)

- A full-attention Qwen3-style transformer at draft hidden size d = 1024 so the target's frozen `embed_tokens` and `lm_head` plug in directly with no projection. DeepSpec's released configs default to 5 draft layers; paper Figure 3 shows a 2-layer DSpark already beating a 5-layer DFlash, so depth is a config axis — start at 2 for draft latency on Metal and ablate 2 vs 5. The drafter never replicates the target architecture: no DeltaNet layers in the draft model.
- Target-context injection per the DFlash equations: hidden states from a set of capture layers are concatenated and fused through a linear projection into the draft hidden space, then injected into every draft layer's keys and values. DeepSpec uses 5 evenly spaced target layers (e.g. [1, 9, 17, 25, 33] for a 36-layer target); for our 24-layer decoder the analog is ~[1, 6, 11, 16, 21], with the already-exported {0, 11, 23} set as the fallback. Final choice is a training-time ablation.
- Input is the anchor (bonus) token embedding followed by γ−1 learned mask-token embeddings; the anchor is treated as the first prediction position, so γ inputs yield γ base logit vectors `U_1..U_γ` in one bidirectional forward pass.
- Default block size γ = 8 locally (paper: γ = 5 in production, 7 offline, gains widen with γ); the scheduler truncates per round, so γ is a ceiling, not a commitment.

### 1.2 Markov sequential head

Low-rank transition bias `B = W_1 W_2` with `W_1 ∈ R^{V×256}` (embedding lookup on the previously sampled draft token) and `W_2 ∈ R^{256×V}`. Position k samples greedily from `U_k + B(x_{k−1}, ·)`, left to right. The sequential loop is γ small steps of a 256-rank lookup plus one 256×V projection — negligible next to the backbone forward. The RNN head variant is explicitly out of scope: the paper measures only marginal gains at long γ and defaults to Markov.

### 1.3 Confidence head

`c_k = σ(w^T [h_k; W_1[x_{k−1}]])` with `w ∈ R^{1024+256}`, trained against the analytical per-step acceptance label `c*_k = 1 − ½‖p^d_k − p^t_k‖₁`. Raw scores are calibrated post hoc with Sequential Temperature Scaling: per-position 1D temperature grid search minimizing the ECE of the cumulative product on a held-out split, applied left to right. Calibrated temperatures ship in the drafter manifest (`calibrate-dspark-confidence-head`).

### 1.4 Hardware-aware prefix scheduler

- Single-request mode (the local default): pick `ℓ* = argmax_ℓ (1 + Σ_{j≤ℓ} a_j) / T_round(ℓ)` where `a_j = Π_{i≤j} c_i` are calibrated prefix-survival probabilities and `T_round(ℓ) = T_draft + T_verify(ℓ)` comes from the measured Metal verification throughput table (`profile-dspark-verification-throughput-table`). The scan is prefix-ordered with early stopping, which preserves the paper's non-anticipating property (no admission decision depends on an uninstantiated future token).
- Batch simulation mode: Algorithm 1 verbatim over R simulated requests (global sort of survival probabilities, greedy admission against SPS(B), early stop on throughput drop), so the load-adaptive behaviour in paper §5 is reproducible offline even though a single local Metal runner has no real concurrency. The paper's ZOS/async adaptations are serving-engine engineering and are explicitly out of scope.

## 2. Training

### 2.1 Data

- Prompts from an open instruction corpus (the paper uses Open-PerfectBlend prompts only); responses regenerated by MiniCPM-V-4.6 in non-thinking mode so labels match the target distribution.
- Generation and feature capture run on **Modal CUDA GPUs** (credits are available) using DeepSpec's own pipeline: `download_and_split.py` pulls Open-PerfectBlend, `generate_train_data.py` regenerates answers against an OpenAI-compatible endpoint (SGLang server on Modal), and `prepare_target_cache.py` captures per-token hidden states via forward hooks — a mechanism that is architecture-agnostic and handles the DeltaNet/full-attention hybrid without changes. Local Metal at ~66 tok/s cannot feed a real corpus; text logits parity against Transformers has already passed, and a held-out sanity check re-scored against Candle-captured traces bounds train/serve feature drift before any large run.
- DSpark training consumes capture-layer hidden states **plus the full last hidden state** (target logits are recomputed through the shared frozen LM head for the TV loss and confidence labels — the paper's §5.1 hidden-state-communication trick); top-k logits are not used by training. The cache costs ~12 KB/token at hidden 1024 with 5 capture layers + last hidden (6 × 1024 × 2 bytes), so even a 100M-token corpus is ~1.2 TB on Modal volumes — manageable, and it shrinks further with fewer capture layers. The current per-token JSON trace exporter stays an inference-side smoke tool; training uses DeepSpec's sharded cache format.
- Scale plan: start at 10–50k regenerated responses (5–20M tokens) and gate scale-up on held-out accepted-length curves; the paper's 1.3M × 10 epochs is reachable on Modal if the curves say it pays.

### 2.2 Objective

`L = 0.1·L_ce + 0.9·L_tv + 1.0·L_conf`, all position-weighted by `w_k = exp(−(k−1)/γ)`: cross-entropy on the ground-truth token, total-variation distance between draft and target distributions (the direct proxy for acceptance rate), and BCE of the confidence head against `c*_k`. Target model, shared embedding, and LM head stay frozen; trainable parameters are the backbone layers, the context-fusion projection, mask embedding, Markov `W_1/W_2`, and `w` — roughly 180M parameters at h = 1024, dominated by the two V×256 Markov factors at the 248k vocab (~127M) rather than the backbone itself.

### 2.3 Trainer

**Reuse DeepSpec** (github.com/deepseek-ai/DeepSpec, MIT, actively maintained — audited 2026-07-10): it ships the DSpark backbone (anchored block attention, mask-token noise embeddings, frozen embed/lm_head sharing), the `VanillaMarkov` low-rank head (rank 256), the confidence head (`AcceptRatePredictor`), the exact three-term position-weighted loss, the full data pipeline, and acceptance-rate evaluation across 9+ benchmarks. Supported targets are Qwen3-4B/8B/14B and Gemma-4-12B; adapting to MiniCPM-V-4.6 is ~300–600 lines of glue (a `build_draft_config` for the nested MiniCPM text config, backbone/embed shims to reach the multimodal wrapper's text decoder, chat-template registration, mask-token choice) — days, not the weeks a from-scratch trainer would cost. The trainer is CUDA-hardcoded (NCCL, `CUDAPrefetcher`, flex_attention + compile), which is exactly the Modal lane; single-GPU works via `CUDA_VISIBLE_DEVICES=0`. At h = 1024 the drafter is tiny (~180M trainable params), so a single Modal GPU trains it comfortably. Pinned deps (`torch==2.9.1`, `transformers==5.10.2`) are behind our env — run it in its own Modal image. Two gaps we own regardless: the **STS calibration fit** (paper-described, not shipped; ~50 lines on top of DeepSpec's ECE/reliability machinery) and the **hardware-aware scheduler** (DeepSeek serving-stack only; ours is the Rust implementation in §1.4). Also relevant: DeepSeek released the paper's Table-1 drafters (`dspark_qwen3_4b_block7` etc.) and a community MLX inference port (`ARahim3/mlx-dspark`) exists for Apple Silicon — both are numerical references for validating our Candle runner, though no checkpoint matches our target so we train our own. No Rust DSpark/DFlash implementation exists anywhere; ours is first.

## 3. Candle/Metal runner

### 3.1 Multi-round speculative loop with state rollback

The full-source audit (2026-07-10) confirmed the runner mutates `conv_state`/`recurrent_state`/`KvCache` in place with no snapshot machinery, so today's speculative runners are single-cycle. The block runner (`integrate-dspark-block-runner`) implements:

1. Prefill once; capture `H_ctx` layers on device (no CPU copies in the hot path — the current trace recorder's per-layer `to_vec1` CPU export is for offline traces only).
2. Snapshot per-DeltaNet-layer `{conv_state, recurrent_state}` (tensor clones) and the KV-cache length.
3. Draft γ tokens (backbone forward + Markov sampling + confidence scores), schedule ℓ via the throughput table, verify the ℓ-token prefix in one target chunk.
4. Full accept → keep advanced state, bonus token becomes the next anchor. Partial accept → restore snapshots, truncate/rewind the KV cache, re-advance the accepted prefix + corrected token as one ≤ℓ+1-token chunk, then continue. The re-advance chunk is the bounded price of losslessness on a stateful recurrent target — an attention-only target would just truncate KV.
5. Correctness gate: exact greedy reconstruction over ≥128 generated tokens on multiple prompts, plus unchanged strict logits parity.

Verification is greedy exact-match (accept while draft argmax equals target argmax), which is exact for greedy decoding — the repo's standing gate. True rejection sampling for temperature > 0 (the paper's T = 1.0 evaluation setting) is a scoped follow-up, not part of v1.

### 3.2 Verify-chunk economics and the kernel lane

Speculation only pays if verifying ℓ tokens costs much less than ℓ decode steps. Measured today: decode ≈ 66 tok/s, prefill ≈ 158 tok/s, so chunk processing is only ~2.4× per-token efficient — dragged down by two audited bottlenecks: `recurrent_delta_rule` runs seq_len > 1 as a per-token loop of ~8 tensor ops per DeltaNet layer, and `depthwise_causal_conv` is an O(seq·kernel) narrow/mul/add loop. `optimize-deltanet-chunked-prefill-and-verify-throughput` addresses both, oracle-gated because a prior conv rewrite changed BF16 reduction order and was rightly rejected. The throughput table is measured before and after; the scheduler consumes whichever table matches the shipped runner.

The candle fork audit (2026-07-10) pins down the mechanics:

- **Full attention**: Metal SDPA kernels exist (`call_sdpa_full` / `call_sdpa_vector` in candle-metal-kernels, routed via `candle_nn::ops`), and the fork's `perf/metal-sdpa-bq8-tiles` branch specifically targets small multi-token q_seq (2–8) — exactly the verify-chunk shape. lmbrrr's naive matmul+softmax attention should move to SDPA (`fix-runner-hot-path-naive-ops`).
- **DeltaNet**: no GLA/delta-rule/chunked-recurrence kernel exists anywhere in candle (CUDA or Metal). The chunked math reference is `candle-transformers/src/models/mamba2.rs` (SSD chunked recurrence via segment-sum); an unregistered `kernel_ssm_scan_f32` in `quantized.metal` is a low-level starting point. Crucially, **a downstream crate can ship its own `.metal` source without forking candle-core**: implement `CustomOp1::metal_fwd`, compile the MSL at runtime via `MetalDevice::new_library_with_source`, cache the pipeline, dispatch. So the chunked DeltaNet kernel can live in lmbrrr and be upstreamed to the fork/candle once proven.
- **KV cache**: no truncate/rollback API exists in candle-nn. `KvCache` writes in place and bumps `current_seq_len`, so a `truncate(n)` that rewinds the counter is a small fork addition (and an easy upstream PR); DeltaNet conv/recurrent state rollback is ours to build in lmbrrr regardless.
- **Quantized matmul hazards**: the Metal mm path (seq_len > 1) hard-asserts F32 activations and has no Q8_1/Q8K support; the mv path loops one dispatch per batch row. BF16-activation qmatmul and a batched GEMV are the highest-leverage fork kernel additions for a quantized-target verify path — relevant once quantization re-enters after DSpark lands.

## 4. Gates

- **Draft quality gate** (before deep runner investment): held-out mean accepted length τ ≥ 2.5 at γ = 8 on local prompt classes; below that, iterate on data/training, not on the runner.
- **Speed gates** (per the repo measurement gate: matched prompts, dtype, device, caps; median of ≥5 iterations): ≥10% end-to-end wall-clock over greedy for prototype value, ≥20% to continue the direction, 1.5–2× as the target given the paper's τ ≈ 5–6 at γ = 7 for 4B-class targets.
- **Comparison matrix** (`benchmark-full-dspark-speedup`): greedy baseline, recurrent-EAGLE smoke, DSpark fixed-γ, DSpark scheduled, and DSpark-with-Markov-disabled as the DFlash-equivalent ablation.
- **Honest-failure clause**: if DSpark does not beat greedy locally, the writeup names which term of `L = (T_draft + T_verify)/τ` failed (draft quality vs verify cost vs draft cost) with measurements, per the experiment-pivot-plan discipline.

## 5. Python vs Candle split

| Concern | Where | Why |
| --- | --- | --- |
| Corpus generation + feature/label capture | Python on Modal CUDA | Throughput; `output_hidden_states`; exact target distributions |
| Backbone/Markov/confidence training | Python (DeepSpec if adaptable) on Modal, MPS smoke | GPU training economics; frozen target |
| STS calibration + reliability diagrams | Python | Held-out sweep, plots |
| Drafter inference, multi-round loop, rollback | Candle/Metal (Rust) | The measured speedup must be real on local hardware |
| Verification throughput table | Rust bench harness | Scheduler input must reflect the shipped runner |
| Scheduler (single-request + batch simulation) | Rust | Runs inside the decode loop |
| DeltaNet chunked kernels | candle fork (Metal) | Verify-chunk cost is the speedup denominator |

## 6. Sequencing

1. **Now (parallel, board width 2):** stand up DeepSpec on Modal (clone, MiniCPM glue, smoke-train on a small corpus) under `train-dspark-semi-autoregressive-drafter`, while `profile-dspark-verification-throughput-table` measures verify-chunk cost locally for γ ∈ {2, 4, 8, 16}.
2. **Then:** STS calibration (`calibrate-dspark-confidence-head`) off the first real drafter; block runner with state rollback (`integrate-dspark-block-runner`); DeltaNet chunk throughput work (`optimize-deltanet-chunked-prefill-and-verify-throughput`) as the table dictates.
3. **Then:** scheduler (`implement-dspark-hardware-aware-prefix-scheduler`) and the four-way benchmark (`benchmark-full-dspark-speedup`).
4. **Background quality lane:** `fix-runner-hot-path-naive-ops` improves the greedy baseline and the verify chunk alike; every change parity-gated.
